CopyPaste ships on macOS, Android, and Windows. Every product capability must provide full functional and UI parity on all three platforms.
Minimal RAM and resource usage is a core product capability. Unnecessary retained memory, CPU work, background wakeups, I/O, and network activity are product bugs even when functional tests pass.
Track existing and new resource-impacting optimizations in `config/optimization-registry.json`. Runtime thresholds belong in `config/runtime-resource-budgets.json`; unresolved budgets or missing native evidence must never be reported as qualified.
Load expensive models, workers, and services only when needed; release them when their work or required background session ends. Bound caches, queues, and retained payloads. Choose process isolation and reuse from measurements, accounting for their memory, CPU, and startup costs.
Measure resource-impacting changes on supported platforms when assessing their resource behavior. Record the application, daemon, and workers separately and as a whole, including peak usage, steady-state usage, and growth. Flutter cache counters or RSS alone do not establish released native memory.
Report missing resource budgets and native evidence explicitly. Do not claim resource qualification without them, invent passing thresholds, or raise budgets to hide regressions. Resource qualification is not a publication gate.
Write all code, code comments, and documentation in English.
Each production module owns one responsibility and exposes the smallest API required by its callers.
Flutter UI uses shadcn_flutter and one shared theme. Maximize reuse of ready-made shadcn components, including navigation, sidebar, scaffold, headers, dialogs, and controls. Verify the package's existing components before implementation. Keep custom UI components to the minimum required for application-specific behavior; never recreate a library component, add pass-through wrappers, or duplicate components per screen.
Treat the shared design system as an enforced contract. Before adding or styling a recurring control, reuse the existing shadcn component, `AppTheme` component theme, and tokens. Styling that must be consistent or is used more than once belongs in `AppTheme` or `app_tokens.dart`, not at individual call sites. Keep local differences as explicit semantic modifiers through the component's public API; do not fork a second visual implementation.
Buttons, inputs, selects, and similar controls in the same row or control group must share one height, including icon-only controls and text scaling; define their sizing in the shared theme.
Every application button must use `Button` from shadcn_flutter. Express hierarchy and shape with `Button` named constructors and `ButtonStyle` modifiers. Do not use the legacy `PrimaryButton`, `SecondaryButton`, `OutlineButton`, `GhostButton`, `LinkButton`, `TextButton`, `DestructiveButton`, `IconButton`, or `SelectedButton` wrappers; Material or Cupertino buttons; custom button wrappers; or raw gesture widgets for button semantics. Shared button padding, typography, icon size, radius, margins, and interaction-state styling belong in `AppTheme`.
Use `AppSpacing`, `AppIconSize`, `AppRadius`, `AppControlSize`, and the shared typography for repeatable UI measurements. Do not introduce raw spacing, application-icon, control-size, or text-size values when a token exists; extend the shared contract when a genuinely new reusable value is required. Brand assets, content media, native OS controls, and feature-specific content geometry are not application UI token violations.
Render clipboard source application identity only through `SourceAppLabel` using the `[application icon] application name` contract. Callers provide the cached icon future; the component owns icon/name alignment and the initials fallback. Do not render the source application icon and name independently in History, inspectors, or Quick Paste.
Use LucideIcons from shadcn_flutter for all application UI icons. Do not add Material, Cupertino, Radix, Bootstrap, or FontAwesome icons or parallel icon dependencies; configure built-in component icons through their public APIs. Brand logos, content thumbnails, and native OS titlebar controls are not application UI icon sets.
Keep business logic, data access, and shared feature state outside widgets; isolate OS integration behind typed adapters. Adapt layout to available space and input while reusing components, state, and actions.
Use one StateView for loading, empty, and error states.
Drawer-level actions must stay in a fixed footer outside the scrollable body, following the History inspector contract. Only the body scrolls; action visibility must not depend on content length.
For CI failures, first identify the earliest causal failure and read the complete logs and primary implementation before changing code.
Never mask CI failures by increasing timeouts, adding retries, skipping coverage or checks, or weakening the required behavior.
CI changes must preserve the required validation, signing, artifact identity and publication contracts. Run `python3 scripts/ci/lint-workflows.py` (actionlint, ShellCheck and current GitHub schema policy), the pinned zizmor security gate, and `python3 -m unittest discover -s scripts/ci/tests -v`; release changes also require `python3 -m unittest scripts/test_release_safety.py scripts/test_linux_qualification_bootstrap.py scripts/test_linux_compositor_runtime.py` and `python3 -m unittest discover -s scripts/release/tests -p 'test_*.py'`.
Preserve exact commit, artifact, signing, and qualification identity across build, qualification, recovery, and publication. Never use caches as release evidence. Register platform changes in the existing platform/release contracts and test their complete required matrix.
Record performance evidence with `scripts/ci/metrics.py`. Compare equivalent workflow inputs and separate cold, warm, unknown-cache, failed, cancelled, build, and publication-only runs. Do not claim acceleration from configuration changes alone.

## Release version changes

`config/release.json` is the only source of application version, build number, and Android version code. Follow the instructions below when preparing a release.

- Run `python3 scripts/release/version.py values` from the repository root to inspect the current identity. If it already contains the requested release version, do not bump again.
- To advance to a new stable version, run `python3 scripts/release/version.py bump <new-version>`. It increments both build counters and synchronizes Cargo, Flutter, all workspace lockfiles (including independent module workspaces), and first-party module application bounds. Do not manually change those generated version fields or bump independent module versions for an application release.
- Cargo must be on `PATH`, with dependencies available for offline lockfile resolution. Investigate resolution failures rather than regenerating lockfiles or updating unrelated dependencies.
- After an intentional edit to the canonical metadata, run `python3 scripts/release/version.py sync`. Run `python3 scripts/release/version.py check` before committing; CI enforces the same check. Preserve explicit module compatibility ceilings.
- When tag creation is authorized, use `python3 scripts/release/version.py tag` from a clean committed checkout. This creates the canonical local tag. Pushing a `v*` tag starts the production release workflow; a version bump alone does not authorize tagging, pushing, or publishing.
